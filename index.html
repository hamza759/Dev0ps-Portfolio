04Case files

Four systems. Four constraints.

An observability platform, an AWS delivery path, an HA database topology and a production deployment on plain VMs. Employer systems are described generically; internal details stay internal.

case 01/observability

production · internal

Centralized observability for 100+ servers

  1. 01 / collectGrafana Alloyon 100+ VMs
  2. 02 / shipMonitor serverdedicated host
  3. 03 / storePrometheus + Lokimetrics + logs
  4. 04 / seeGrafanadashboards

blackbox / http · tcp · icmp → master health

Problem

With more than 100 Linux servers and VMs across on-premises and AWS, detection depended on someone noticing. The goal was one place to see metrics, logs and connectivity, with probes that catch a dead or isolated node quickly.

What I built

A dedicated monitoring server running Prometheus, Loki and Grafana. Grafana Alloy runs on every VM and ships logs and metrics locally to that server. Blackbox Exporter on replica servers probes the master over HTTP, TCP and ICMP. Grafana surfaces CPU, memory, disk, top processes, logs, ICMP ping latency and probe duration with dashboards and logs.

A separate ELK stack — Filebeat, Logstash, Elasticsearch and Kibana — handles centralized application logs.

Stack

  • Prometheus
  • Grafana
  • Loki
  • Grafana Alloy
  • Blackbox Exporter
  • ELK
  • Linux

Result

100+ servers in one view, mean time-to-detection cut by 60%, and a single dashboard for master/replica health, logs and connectivity.

Internal system — no public repository. Ask me about it.

case 03/databases

production · internal

HA PostgreSQL with Patroni

Problem

A single PostgreSQL node is a single point of failure. Replication, failover and restores had to be understood and recoverable, not just configured once.

What I built

A Patroni-managed PostgreSQL cluster: one primary and two replicas, with etcd as the coordination layer that decides the leader. HAProxy routes writes to the primary and reads to replicas. I set up replication manually, handled replication failure recovery, and built pg_dump backups to NFS, including restores into newer PostgreSQL versions.

Stack

  • PostgreSQL
  • Patroni
  • etcd
  • HAProxy
  • pg_dump
  • NFS
  • Linux

Result

Replication failures can be recovered, the cluster has a clear leader, and backups are restorable into newer PostgreSQL versions.

Internal system — no public repository. Ask me about it.

case 04/production vms

production · internal

Production application deployment on VMs

Problem

No managed platform: the proxy, application servers and background workers all run on VMs, so releases, process supervision, TLS and health checks have to be deliberate.

What I built

Nginx in front of uWSGI and Daphne, with Celery Worker and Beat supervised as systemd services. Daily releases with health checks, plus Ansible playbooks for configuration changes on database servers and remote toll-plaza booth PCs. On AWS, EC2 instances inside a VPC run PostgreSQL, Redis and the backend directly on the VM. On Hostinger VPS, I manage custom domains, SSL and Cloudflare. I also host an LLM on-premises.
